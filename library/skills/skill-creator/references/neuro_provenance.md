# Run material → skill files (neuroscience run-derived skills)

How a finished NeuroScientist Level-1 run is packaged into a skill folder. This is
the shared contract between the automated backend
(`internagent/modules/targeted_skill/save_skill.py`) and any human editor refining
the skill afterwards.

## Sources
- `state.json` — `question` (+`question_history`), `data_info` (dataset metadata,
  free text), `plan` (`plan_markdown`, `summary`, `warnings`), `code`
  (`code_files`, `statistics`), `artifacts`, `validation(s)`, `image_analyses`,
  `conclusions`, `resource_profile`, `deliverables`, `targeted_skill`,
  `deep_research_context`.
- On disk in the run dir — `generated_code.py` (the actual method), `statistics.json`,
  `conclusions.json`, `plan.md`, `figure.*`.
- Dialogue digest — user turns + corrections + the `neuro_*` tool-call sequence
  (captured via `ctx.sessionManager.getBranch()`), for tacit intent not in state.json.

## Frontmatter (reconciled, dual-format)
```yaml
---
name: <pi_name>                 # kebab, <=64; e.g. ns-ana-mouse-spike-pca-population-trajectory
description: "<= 1024 chars, no angle brackets"
metadata:
  provenance: expert_run
  run_id: <run_id>
  smmt: {stage, species, modality, method, target}
  triggers: [ ... 5 ... ]
  tags: [ ... 4-6 ... ]
  version: "1.0"
---
```
Top-level keys are limited to `name`/`description`/`metadata` (pi allow-list); the
substrings `triggers:`/`tags:`/`version:` under `metadata` satisfy the repo validator.

## scripts/
- `scripts/run_analysis.py` ← the run's `generated_code.py` (verbatim).

## references/ (all 9 are required by `validate_skills.py`; each >= 50 chars)
| file | source |
|---|---|
| `question.md` | `question` (+ `question_history`) |
| `paper_context.md` | `deep_research_context`, else "run-derived; no source paper" |
| `repo_context.md` | `targeted_skill` used during the run, else "run-derived; no source repo" |
| `connection_analysis.md` | plan summary/warnings + how the code maps to the question + dialogue digest |
| `reproduction_plan.md` | `plan.md` / `plan_markdown` |
| `paper_structured_summary.md` | `data_info` + `conclusions` |
| `paper_figure_methods.md` | `deliverables`/artifacts + `image_analyses` |
| `repo_overview.md` | SMMT rationale + `resource_profile` + dependencies parsed from the code imports |
| `repo_file_summaries.md` | statistics keys + code file inventory |
| `references/matched_files/` | copies of `generated_code.py`, `statistics.json`, `conclusions.json` |

## metadata.json
`{tag, provenance:"expert_run", run_id, smmt, pi_name, scripts[], references[], yaml_metadata{name,description,triggers,tags}}`

## Dual registration
- Loader: `library/skills/from_expert/INDEX.md` is regenerated by
  `internagent/modules/targeted_skill/index_generate.py`; the dir is listed under
  `modules.targeted_skill.extra_skill_dirs` in `config.yaml`.
- pi: each saved skill's OWN directory (`library/skills/from_expert/<folder>`) is
  appended to `skills` in `.pi/settings.json` on save — NOT the parent library, so
  pi never scans the parent's loose files (INDEX.md, .gitkeep) as skills. The skill
  is then invocable as `/skill:<pi_name>` on the next pi launch.
